# Memory the hardware reads and writes

Some hardware state is not in registers but in RAM: structures whose format
the silicon defines and which the CPU and the hardware hand to each other.
They are part of the hardware just as registers are, and need the same
discipline: one reviewed description, evidence for every field, `_OPAQUE` for
what is unknown, generated accessors, no hand-written masks. This document
describes how the register model, the PAC and the HAL describe them.

## Which structures

| Structure | Shared how |
| --- | --- |
| Wi-Fi DMA descriptor (12-byte node: control word, buffer address, next) | CPU arms, the walker fills, owner bit 31 hands it over |
| Wi-Fi RX control prefix (metadata the MAC writes at the start of each received buffer: RSSI, PHY info, local timestamp) | hardware writes, CPU reads after completion |
| Wi-Fi TX descriptor words (flags, security, HE control, rate context) | CPU writes, hardware reads at transmission |
| A-MPDU internal and external descriptors | CPU builds, hardware walks |
| BLE controller exchange memory (buffer headers, packet prefixes, scheduler items, link states, the device table, the direction-finding workspace) | CPU and controller both, by protocol |
| IEEE 802.15.4 frame buffers (length byte, PSDU) | CPU and engine |

The Wi-Fi DMA descriptor, RX control prefix, TX metadata head and the known
flags, priority and security fields of the ordinary TX descriptor prefix are
generated from the register model. Both internally buffered and externally
backed A-MPDUs use the same generated TX DMA descriptor; their HAL entry
types describe software inputs, not separate hardware layouts. Per-queue
PLCP1, length-control, power and PTI words use generated register fields.
BLE buffer headers, RX/TX packet prefixes, scheduler items and contexts,
link states, PHY environment, resolving list, device table and DF workspace
also use generated layouts in the controller-memory owner; role reset and
allocation images are constant generated values built with `with_*`. The three
PHY environment lookup buffers (channel frequency offsets, packet-prefix
airtimes and RX address delays) use generated byte layouts as well.
Unassigned fields are positional and opaque.
The unassigned TX fields and 802.15.4 frame buffers
retain their existing descriptions, with fields named by offset where their
meaning is unknown. The PHY's RFPLL codes, frequency-memory records and analog-I2C
command words also have generated value accessors. Register-specific
composed domains preserve overlapping ROM publications, including the
signed capacitor correction's spill into the frequency-memory mode byte.

## How it differs from MMIO

- **No fixed address.** An owner places the structure (a static, an arena, a
  ring) in a region the hardware can reach; the hardware learns the address
  from a register (a descriptor base) or from another structure (a `next`
  link).
- **A placement rule instead of an address.** Size, alignment and the region:
  the DMA window, internal SRAM only, a 4-byte boundary.
- **Shared by protocol.** Each field has a writer (the CPU, the hardware, or
  both at different phases) and a handover: a bit, an order of writes, a
  fence, a doorbell. Registers have access types; these structures have
  phases.
- **Two kinds of access.** While the hardware may touch a word, the CPU uses
  volatile word access. After a proven handover (a completed RX unit), the
  bytes are plain memory the CPU owns.

## Three layers

Same split as for registers: the model says what lies where and who writes
it; the HAL says in which order and who owns it.

### 1. Layout: the register model and the generated PAC

A **memory layout** describes RAM beside the MMIO block types:
`chips/<chip>/registers/layouts/<name>.toml`, included by the chip root
`chip.toml`, whose `[[layout-placements]]` place it in RAM regions.

A field may declare `values = [{ name = "COMMON_TX", value = 2 }]` for
established hardware encodings. Its resolved field review supplies the
sources. The generated word/range image exposes `<FIELD>_<VALUE>` in the
field's native type, plus `<FIELD>_WIDTH` and `<FIELD>_MAX`; these are the
dictionary and geometry HAL uses. Sequence-specific images remain in HAL.

```toml
[layout]
name = "WIFI_DMA_DESCRIPTOR"
description = "The 12-byte node the Wi-Fi DMA walker follows."
size = 12
align = 4

[[layout.words]]
name = "CONTROL"
offset = 0
access = "shared"                   # volatile while the hardware may touch it

[[layout.words.fields]]
name = "OWNER"
bits = "31"
writer = "cpu"                      # the hardware reads it, never clears it
description = "1: the walker may fill this node; it stops at a node with 0."

[[layout.words.fields]]
name = "RX_DONE"
bits = "30"
writer = "hardware"

[[layout.words.fields]]
name = "SOSF"
bits = "29"
writer = "phased"
phases = [{ name = "arm-rearm", writer = "cpu" }, { name = "receive", writer = "hardware" }]
description = "Vendor sosf bit, cleared on rearm. The receive phase conservatively permits an unknown hardware writer; no store or physical effect is established."

# SOURCE: BLOB_RX_DESCRIPTOR_DIAGNOSTIC_NAMES in the S31 register model.
[[layout.words.fields]]
name = "OFFSET"
bits = "28"
writer = "phased"
phases = [{ name = "arm", writer = "cpu" }, { name = "receive", writer = "hardware" }]
description = "Vendor offset bit; encoding, units and effect unknown. The receive phase conservatively permits an unknown hardware writer; no store is established."

[[layout.words.fields]]
name = "LENGTH"
bits = "27:14"
writer = "hardware"

[[layout.words.fields]]
name = "SIZE"
bits = "13:0"
writer = "cpu"

[[layout.words]]
name = "BUFFER"
offset = 4
access = "shared"
fields = [{ name = "ADDRESS", bits = "31:0", writer = "cpu", placement = ["dma-window"] }]

[[layout.words]]
name = "NEXT"
offset = 8
access = "shared"
fields = [{ name = "ADDRESS", bits = "31:0", writer = "cpu", points-to = "WIFI_DMA_DESCRIPTOR" }]
```

Byte-oriented layouts (the RX control prefix) declare `[[layout.bytes]]`
ranges instead of words, with `access = "owned"`: the CPU reads them only
after a handover.

A field written by both participants at different phases declares
`writer = "phased"` and an ordered, nonempty `phases` list. Each phase has a
unique name and one writer (`cpu` or `hardware`), for example:

```toml
writer = "phased"
phases = [{ name = "arm", writer = "cpu" }, { name = "complete", writer = "hardware" }]
```

The generated documentation records these phases; the HAL enforces their
order and handover. A single-writer field does not declare phases.

A fixed array declares `[layout.array]` with `element = "<LAYOUT>"` and
`count`. Its element is a shared-word or owned-byte layout; size is the
element size times count, and alignment and placement match the element.
A shared-word array exposes checked `entry(index)` references and can be a
`DmaRef` target. An owned-byte array decodes a fixed byte buffer through
checked `entry(index)` element decoders, with a generated `COUNT`. Its writer
borrows one element writer at a time when the element has CPU-written fields.
The byte array remains a buffer addressed by `DmaWindowAddress`.
The channel-frequency lookup uses this indexed form; the packet-start and
RX-address-delay lookups retain their named PHY-mode slots in the model.

A BLE link to a structure declares `points-to = "<LAYOUT>"` and
`encoding = "ble-compressed"` on a 20-bit field. A pointer to a byte buffer
uses `placement = ["dma-window"]` with that encoding instead, including a
pointer to the beginning of a packet with its RX or TX prefix. Its nonzero value is a
word index: the CPU address is `0x2f000000 | (index << 2)`. Zero is no link.
The link builder takes `Option<DmaRef<Layout>>`; the buffer builder takes
`DmaWindowAddress`. Both check the encoding and preserve the surrounding
bits. A getter decodes an address without creating a
reference; hardware-written links still need validation against their arena.

Every field gets a `[[review]]` like a register field: naming, sources,
provenance, accuracy, completeness. An offset or bit position whose physical
meaning is unknown uses `accuracy = "positional"` and an opaque name.
A fact measured on the stand is evidence
of a new class, `stand`, citing the chip's `notes/` and the runs; vendor
facts keep their `BLOB_*` ids.


A layout can declare `[layout.review]` as the default review for its own
identity, words or byte ranges, and fields. The keys are `sources`,
`provenance`, `accuracy`, `completeness` and `naming`. A separate
`[layout.review.opaque]` supplies the complete default for an explicitly
opaque word, range or field:

```toml
[layout.review]
sources = ["REVIEWED_LAYOUT_SOURCE"]
provenance = "reviewed"
accuracy = "exact"
completeness = "complete"
naming = "descriptive"

[layout.review.opaque]
sources = ["REVIEWED_LAYOUT_SOURCE"]
provenance = "reviewed"
accuracy = "positional"
completeness = "unknown"
naming = "opaque"
```

An entity opts into the opaque default with `opaque = true` on its word,
byte-range or field declaration. This selects that entity's review only;
it does not infer opaque status from a name or mark its children. Opaque
names still have to match their position. The opaque default is independent
of the ordinary default; its keys are not merged with that table.

An explicit `[[review]]` replaces the applicable default in full, including
omitted keys. Defaults belong to this layout alone. Publication still
requires a complete resolved review for every entity. Unknown keys,
reviews for nonexistent entities, duplicate reviews and an explicit review
identical to its applicable default are errors.

The root's `[[ram-regions]]` hold the RAM regions the layouts name
(`dma-window`), so the DMA window has one source.

The generator emits, in the chip's PAC (`generated.rs`):

- a `#[repr(C, align(N))]` type of the layout's words, `Zeroable` by derive
  over `oer-memory`'s volatile cells, with compile-time size and alignment
  checks;
- for each `shared` word, a cell with volatile `read() -> Value` and
  `write(Value)` only; for each word a `Value` type with typed getters and
  `with_*` builders, as the PAC's register values have;
- for `owned` byte layouts, a decoder from `&[u8; N]` (fixed-size arrays, no
  panics), the shape `prefix.rs` already follows by hand; a byte layout
  with CPU-written fields also gets a writer over `&mut [u8; N]` with typed
  setters;
- the placement as constants the HAL checks against (`StableDmaRange`,
  `placement.rs`).

The PAC supplies layout types and accessors. Ordering, fences and the
CPU/hardware ownership protocol belong to the HAL.

### 2. Protocol: the HAL

Hand-written and typed, as in `rx_ring.rs`, `rx_storage.rs` and the TX
storage: the ownership machine (armed, completed, detached, rearmed), the
publication order (buffer address, then `CONTROL` with `OWNER = 1`, a fence,
the doorbell), the proofs (`RxDmaWalkerStopped` naming its arena), the
reserved descriptor behind `BASE`. The HAL reaches the structures only
through the generated types; `CLAUDE.md`'s rule against local masks extends
to hardware-shared memory.

### 3. Placement: platform and HAL

A DMA static is declared with the chip HAL's `dma_static!`: a zeroed
`DmaStatic<T>` in a `.dma.bss.<block>` section (the macro refuses any other
section name), claimed once as a `Placed<T>`. The register generator writes
each chip's `layout/linker/dma-window.x` from the model: the `dma-window`
region and the low address bits its pointers keep. The
runtime linker script includes it and asserts that all DMA storage lies in
the window and holds no address whose low address bits are zero; the
runtime link uses `--orphan-handling=error`, so a mistyped section name
cannot leave a static unplaced. A storage that publishes its own addresses
binds from a `Placed` value: the receive static is the driver's arena and the
HAL's RX DMA storage placed together (`WifiRxStatic`), split once
(`Placed::split`); only a `PlacedRxDma` (`RxDmaStorage::place`) prepares a
ring, and the TX storages pin only placed storage (`TxDmaStorage::pin`,
`AmpduDmaStorage::pin`). Host models use `Placed::host` (test support).
`DmaSpace` and `StableDmaRange` stay. The run-time window checks and the
firmware placement warning's DMA rules are gone: the link proves what they
checked. `cargo fw` refuses an image that enables `test-support`.

The BLE `Engine::new::<ChipDma>` consumes the clocked register owner and
one `Placed<BluetoothArena>` from `.dma.bss.bluetooth`. Its nested pairs
hold PHY storage, device table, DF workspace, role pools and RX chains;
only the engine splits their ownership. Pool, chain and scheduler capacities
remain const generics. Claiming initializes every graph from zero, including the PHY
lookup buffers, before any publication. The owner derives typed addresses
from its actual fields; checks concern allocation membership and compressed
encoding. Physical placement is proved by the same linker assertions. Native
tests consume `Placed::host` with a distinct `HostDma<BASE>` per arena;
synthetic bases and extents are checked at compile time.

The S31 802.15.4 driver owns the MAC token with the placed
`Ieee802154EngineBuffers` of `.dma.bss.ieee802154`. HAL builds the 23 typed
addresses once from the allocation's actual frame projections (21 receive
slots including the stub, TX and enhanced ACK). The common engine sees only
`Ll::Address: Copy + Eq` and selects the table entry by slot. Host DMA inputs
are matched against that table; an unknown identity is rejected without a
panic. The driver's combined owner exposes operation entries, frames and slots;
the MAC and its storage cannot be borrowed separately.

TX prepare and start authorities carry `DmaRef<WifiTxDmaDescriptor>` through
the chip-independent `PreparedTxDma<Address>` and `HardwareOwnedTxDma<Address>`
traits. `Placed` supplies a stable range whose extent comes from its complete
allocation; descriptor and buffer ranges are checked subranges of it. The
range proof retains the storage lifetime without holding a Rust reference
that would alias the owner's mutable borrow. Only the final PAC register
publication extracts the descriptor address bits.

A transmit pool is placed the same way: `PlacedTxPool::pin` takes a
`Placed<PinnedDmaTxPool>`, and its radio leases are `PlacedTxLease`s. The
sealed `PlacedBacking` marks them, and the pool's wrappers around them, as
buffers in the DMA window; the A-MPDU retention takes only `PlacedBacking`s and
publishes their addresses without a window check. The ordinary descriptor
(`TxDmaStorage`) holds no buffer of its own: it attaches one `PlacedBacking`
while free and publishes that lease's address. The S31 Wi-Fi port writes
every MPDU and aggregate subframe into one placed pool and publishes it
through its queue's descriptor or an aggregate chain. A buffer lent from outside
placed storage has no source yet; it returns as a loan type, checked once where
the loan is made, with the first such buffer.

## Bluetooth controller memory

`oer_esp32s31_hal::bluetooth::engine` retains the component codecs and
CPU/controller ownership protocol. The BLE driver enables the HAL's
`bluetooth-engine` feature; Wi-Fi images retain their dependency graph.
One engine retains the register token and the entire placed arena through
HAL initialization, PHY activation, runtime workers, stop and reset. Private
components bind PHY, DF, device table, role pools and receive chains inside
that same allocation; no standalone PHY/DF runtime owner is exported.
The driver carries the arena's capacity and lease brands as a generic memory
type through every lifecycle and terminal failure state.

Driver role builders select profiles, phases, channels and event windows.
Their detached values contain no layout reference or inspectable pointer.
HAL encodes physical fields and checks binding anchors before committing a
value. Raw binding constructors, layout projections and address publication
primitives are private; PHY/DF, table and RX publication goes through the
owning engine. Debug output of opaque projections and
scheduler steps does not reveal address-bearing words.

Generative pool and epoch scopes bind affine leases to one pool installation;
release consumes the lease. Hardware heads resolve against submitted items
inside HAL and return logical identities. An acquisition generation prevents
an old identity from naming a reused slot. Finished-list fences also carry
the capturing engine installation epoch, allocated without wrap; an old fence is rejected before any completion
read or CPU return. Retirement requires a stopped, empty scheduler, no
physical transaction and idle controller-time and finished-list workers.
Reset returns the same complete `Placed` allocation after ending the old
pin contracts and zero-initializing its backing in place. Any unconfirmed
stop or failed reset keeps the entire arena quarantined with its registers.
The asynchronous scope helpers
retain these brands across task suspension without allocation. Physical
scheduler transactions remain in the P2 engine. The stable P3 half alone
accesses IRQ registers. Bank changes and fresh diagnostic samples cross a
static HAL request/reply slot through the shared radio doorbell. Each reply
carries the installation epoch and a non-repeating command number, and only
its readiness notification coalesces. An abandoned exchange keeps its seat
and prevents arena retirement. Both quiet endpoints reunite after stop and
route removal before reset and channel reuse.

## Where registers, layouts and the protocol meet

- **One IP block, one description.** A layout belongs to the peripheral that
  consumes it, beside its registers. A register field the hardware reads as
  a pointer names its target in the model (`points-to =
  "WIFI_RX_DMA_DESCRIPTOR"`), and the PAC accessor then takes a typed
  reference (`DmaRef<WifiRxDmaDescriptor>`), never a bare `u32`.
- **The protocol is that block's HAL engine.** One HAL type owns both the
  block's register token (from the ownership root) and its placed arena; the
  base register, the doorbell and every descriptor publication are its
  methods. Neither the registers nor the arena is reachable apart from it.
  Drivers above see leases, cursors and outcomes, never addresses.
- **Placement is proved before run time.** An arena is declared through a
  macro that puts its static into the block's `.dma.bss.<block>` section; a
  linker `ASSERT` keeps the section inside the DMA window and off a base whose
  low DMA-address-field bits are zero. `DmaRef<T>` is built only from such a
  placed static, and buffer addresses are typed offsets inside the same arena, so they are
  valid by construction. Size and alignment are compile-time checks. The
  run-time address checks (`descriptor_address_valid`, the run-time part of
  `placement.rs`, the firmware placement warning) are removed. What the
  hardware writes back (`NEXT`, `LAST`) is outside input and stays checked,
  against the arena rather than the window. Host tests keep the `HostDma`
  space with the same types.
- **The unsafe boundary.** Volatile word access lives in `portable/mmio`;
  generated layout accessors use its safe API. The HAL holds the one
  placement constructor (justified by the linker assertion and a single
  `take`) and the protocol core, where a CPU view of a buffer is created
  after the completion proof and where a buffer is handed back to the
  hardware. Crates above the HAL carry `#![forbid(unsafe_code)]`.

## Model access

S31 layouts live in `chips/esp32s31/registers/layouts/` and are included by
`chip.toml`. Host tools load the same register model through
`oer_registers_model::Chip::load`; generated layout accessors live in the
PAC's `generated.rs`.
